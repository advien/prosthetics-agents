# Проект: мультиагентные системы для assistive robotics / протезирования и ортезирования

## Context

Цель — построить показательный проект(ы), демонстрирующий(е) навыки AI/agentic engineer: проектирование мультиагентных архитектур, протоколы обмена сообщениями между агентами, разделение ответственности, human-in-the-loop и safety-паттерны. Аудитория двойная: (1) работодатели (портфолио для поиска работы AI engineer) и (2) приёмные комиссии магистратур по AI/robotics/health-tech — то есть проект должен читаться и как инженерный кейс, и как заявка с исследовательской нагрузкой (обоснованные решения, оценка результата, этическая рефлексия).

Пользователь работает в сфере ассистивной робототехники, протезирования и ортезирования — тема должна быть привязана к этой нише, а не быть generic-агентным ботом.

Три кандидата-направления были рассмотрены (A — управление протезом в реальном времени, B — клиническая система подбора протеза/ортеза, C — оркестрация кастомного производства). Пользователь попросил не выбирать одно, а сравнить все три и построить путь "быстрый MVP → итерации → полноценный проект", плюс рекомендацию стека (предпочтений нет).

## Сравнение трёх направлений

| Критерий | A. Управление протезом в реальном времени (симуляция) | B. Клиническая система подбора протеза/ортеза | C. Оркестрация кастомного производства (скан → CAD → печать → QA) |
|---|---|---|---|
| Близость к "робототехнике" | Максимальная — классический control loop | Низкая — нет физического контроля | Средняя — оркеструет физический процесс изготовления |
| Насколько раскрывает LLM-агентов (рассуждение, коммуникация на естественном языке) | Средняя — больше классических control-агентов, меньше NL-рассуждений | Высокая — богатое клиническое рассуждение, работа с текстом/данными пациента | Высокая — планирование и tool-use через этапы пайплайна |
| Реализуемость без реального железа | Средняя (нужен генератор синтетических EMG/IMU-сигналов) | Высокая (синтетические/обезличенные профили пациентов) | Высокая (открытые/синтетические 3D-сканы, open-source CAD-инструменты) |
| Демонстрируемый артефакт | Дашборд с replay телеметрии | Чат/дашборд + сгенерированный клинический отчёт | Реальный CAD-файл / рендер — самый осязаемый результат |
| Нарратив "safety-critical" (силён для грант./грэд заявок) | Очень сильный (safety-supervisor, fail-safe) | Средний (клиническая ответственность, human-in-loop) | Средне-слабый (QA/допуски) |
| Новизна / отличие от типовых портфолио | Высокая — мало кто делает agentic control demo | Средняя — clinical-decision-support агентов уже много | Высокая — agentic manufacturing pipeline для протезов почти не встречается |
| Время до MVP | 3–5 дней (мок-сигналы, 3–4 агента) | 2–4 дня (самый быстрый — чистый текст/данные) | 5–8 дней (нужна интеграция CAD-тулинга) |
| Привлекательность для магистратур (biomechatronics/rehab robotics) | Высокая | Средняя | Средне-высокая (medical device / manufacturing engineering) |
| Социальный impact-нарратив | Средний | Высокий (доступ к качественной помощи) | Очень высокий (доступное протезирование в ресурсно-бедных регионах — сильная тема для global health/humanitarian robotics) |

**Вывод:** ни один вариант не доминирует по всем осям — но они естественно выстраиваются в последовательность по сложности и типу демонстрируемого навыка. Решение пользователя: **делать все три, в порядке B → C → A** — от самого быстрого и NL-насыщенного (B) к оркестрации физического производства (C) и затем к самому "хардкорному" робототехническому модулю — control loop в реальном времени (A). Это даёт нарастающую сложность и по ходу проекта охватывает весь спектр: от рассуждающих агентов на тексте/данных, через агентов с tool-use над файлами/CAD, до safety-critical control-агентов.

## Рекомендуемая стратегия: поэтапная градация (B → C → A)

### Этап 0 — Фундамент (1 день)
Лёгкий скелет оркестрации: определить схему сообщений между агентами (JSON-контракт: кто кому что передаёт), выбрать стек (см. ниже), настроить логирование inter-agent коммуникации для последующей визуализации — это то, что физически "показывает" мультиагентность на скриншотах/видео для портфолио. Этот скелет переиспользуется во всех трёх направлениях, поэтому вложение в него окупается сразу на Этапе 1.

### Этап 1 — MVP: клиническая система подбора протеза/ортеза (B), 3–5 дней
Самый быстрый путь к рабочей демонстрации без зависимости от железа. Агенты:
1. **Intake Agent** — структурирует данные пациента (уровень ампутации, K-level активности, образ жизни, сопутствующие условия) из свободного текста.
2. **Biomechanical Analysis Agent** — оценивает биомеханические требования (нагрузка, диапазон движения, тип походки) на основе структурированных данных.
3. **Recommendation Agent** — подбирает тип устройства/компонентов по упрощённому справочнику-каталогу.
4. **Documentation Agent** — генерирует клинический отчёт/обоснование (в т.ч. для страховой).
5. **Safety/Review Agent** — проверяет рекомендацию на противоречия/красные флаги, эскалирует к человеку при неуверенности.

Коммуникация: общий "patient record" объект передаётся по графу, каждый агент читает/пишет свои поля; параллельно пишется лог сообщений для демо-визуализации графа общения. **Важно:** явный disclaimer, что это исследовательский прототип, не сертифицированный клинический инструмент — эта оговорка сама по себе усиливает нарратив "responsible AI" для грэд-заявки.

### Этап 2 — Углубление + расширение: оркестрация производства (C), интеграция с B, несколько недель
Сначала докрутить B до research-grade уровня, затем пристыковать C как продолжение "пути пациента" — от консультации до готового к производству файла:
- Добавить **Follow-up/Monitoring Agent** (B) на синтетической телеметрии устройства.
- Добавить human-in-the-loop шаг одобрения врачом (B).
- Собрать небольшой eval-harness: тестовые кейсы с "эталонными" рекомендациями, сравнение агентной системы с baseline (одиночный промпт) — отличает student-проект от research-grade работы.
- Апгрейд UI: Streamlit → лёгкий веб-дашборд с живой визуализацией обмена сообщениями.
- Пристыковать направление C, продолжая граф из B:
  6. **Scan Processing Agent** — обрабатывает 3D-скан культи (mesh, через `trimesh`).
  7. **CAD Generation Agent** — параметрически генерирует геометрию гильзы/компонента (`CadQuery`/`build123d`).
  8. **Manufacturing Scheduling Agent** — планирует этапы печати/фрезеровки.
  9. **QA Agent** — проверяет геометрические допуски перед отправкой в производство.

Результат Этапа 2 — сквозная демонстрация B→C: от текстового описания пациента до сгенерированного и проверенного производственного файла. Уже это самостоятельно сильный флагманский кейс.

### Этап 3 — Продвинутый модуль: управление протезом в реальном времени (A), долгосрочно
Самый "хардкорный" робототехнический слой, венчающий проект. Агенты: **Sensor-Fusion Agent** (обработка синтетических EMG/IMU-сигналов) → **Intent-Recognition Agent** → **Motion-Planning Agent** → **Safety-Supervisor Agent** (может заблокировать/скорректировать команду) → **Adaptation Agent** (обучается на паттернах пользователя). Работает на другом временном масштабе и с другим типом данных, чем B/C, поэтому реализуется как отдельный модуль/демо (например, отдельный notebook + симулятор), с общей инфраструктурой логирования сообщений из Этапа 0 — так весь проект остаётся визуально и архитектурно единым, даже если A не интегрирован в общий пайплайн буквально. Этот этап и добавляет самый сильный safety-critical нарратив (важно для grad-заявок в biomechatronics/rehab robotics) и закрывает весь заявленный диапазон: NL-рассуждение → tool-use/производство → real-time control.

## Рекомендуемый стек

- **Оркестрация:** LangGraph (Python) — явный граф/state machine, топологию общения агентов легко нарисовать и объяснить на собеседовании или в SOP. Более узнаваемое имя в индустрии и академии, чем узкоспециализированные альтернативы. CrewAI — как более простая альтернатива, если приоритет — скорость прототипирования, а не прозрачность протокола. Claude Agent SDK — вариант, если хочется нарратива "built natively with Claude" (уместно, если целитесь в Anthropic-смежные роли).
- **LLM backend:** Claude через Anthropic API — с осознанным выбором модели по агенту (например, Sonnet для агентов с содержательным рассуждением, Haiku для лёгких/дешёвых агентов вроде Intake) — сам факт такого выбора стоит явно проговорить как инженерное решение (cost/latency-aware design).
- **UI на MVP:** Streamlit (быстро, минимум кода) → на Этапе 2 полноценный дашборд, если нужно.
- **Domain-инструменты для C:** `trimesh` (обработка 3D-сканов), `CadQuery`/`build123d` (параметрический CAD скриптуется на Python).
- **Наблюдаемость:** структурированный JSON-лог всех сообщений между агентами + визуализация (таймлайн/граф) — это буквально то, что должно быть в скриншотах и демо-видео.
- **Репозиторий:** отдельная папка/git-репозиторий с самого начала, README с диаграммой архитектуры, короткий ARCHITECTURE.md на каждый этап — материал одновременно для резюме и для эссе в магистратуру.

## Что подчёркивать для каждой аудитории

- **Работодатель:** чистая архитектура, читаемый код, тесты/eval, продуманный выбор стека и моделей, живое демо.
- **Магистратура:** обоснование дизайна, сравнение с baseline, этическая рефлексия (disclaimer про клиническое применение), связь с реальной проблемой в индустрии (доступность протезирования), возможно короткий write-up в духе mini research report.

## Следующие шаги (когда будете готовы перейти от планирования к реализации)

1. Завести рабочую папку/git-репозиторий под проект.
2. Реализовать Этап 0 (контракт сообщений + логирование) и Этап 1 (MVP направления B) — самый быстрый видимый результат.
3. Уже на этом этапе сделать первый скриншот/демо-видео для портфолио — не дожидаясь Этапов 2–3.
4. Итеративно наращивать по плану выше, документируя каждый этап отдельным коммитом/README-секцией.
